# Mytalk 开发日志 — 2026.10.09

**开发主题：TCP 消息传输可靠性、并发安全及服务端架构优化**

## 一、今日完成的工作

### 1. 完善自定义通信协议

继续使用基于 TCP 的文本通信协议，以 `\n` 作为消息结束标志，以 `|` 作为命令分隔符。

目前支持：

- `AUTH`：客户端身份认证
- `NAME`：注册昵称，检查重名
- `CHAT`：群聊消息
- `MSG`：用户之间的私聊
- `LIST`：查询在线用户列表

编写并完善 `praseMessage()`，将完整消息解析为 `struct_message`，统一提取 `command`、`target`、`data`，避免在业务函数中反复使用 `find()` 和 `substr()`。

对非法消息进行基本格式校验，修复了 `LIST|` 因参数为空而被错误拒绝的问题。

### 2. 实现 sendAll()，解决 TCP 部分发送问题

认识到 TCP 是字节流协议，单次 `send()` 不保证提交全部数据。

实现 `sendAll()`：

- 使用 `sent` 记录已经成功提交的字节数。
- 通过循环继续发送剩余字节。
- 根据 `send()` 返回值判断发送是否完成。
- 使用 `errno`、`EINTR` 处理被信号中断的系统调用。
- 使用 `MSG_NOSIGNAL` 防止发送时产生的 `SIGPIPE` 默认终止服务端进程。

学习了 Linux 系统调用的错误处理机制，理解 `errno`、`EINTR`、`EPIPE` 等概念。

### 3. 重构客户端连接管理

原来使用：

```cpp
vector<struct_client> clients;
```

现在改成：

```cpp
vector<shared_ptr<struct_client>> clients;
```

学习了 C++11 智能指针 `shared_ptr` 的基本原理及引用计数机制。

理解了：

- `mutex` 不允许直接复制。
- `shared_ptr` 复制的是共享所有权，不是客户端对象本身。
- 即使客户端从 `clients` 中删除，其他线程已经持有的 `shared_ptr` 仍能保证结构体对象存活。
- 客户端对象的生命周期和操作系统 socket 的生命周期并不是一回事。

同时修改了客户端结构体和业务函数的参数传递方式。

### 4. 完善多线程同步机制

明确了两种互斥锁的职责。

**clients_mutex**

保护在线客户端数组以及共享的昵称、注册状态，避免遍历期间执行 `erase()`、`push_back()` 等操作造成数据竞争。

同时将昵称重复检查和注册操作放在同一个临界区中，避免两个用户同时注册相同昵称。

**send_mutex**

每个客户端拥有独立的发送锁，解决多个服务端线程同时向同一个 socket 发送消息时可能产生的消息交错。

封装 `sendToClient()`，统一发送入口，避免业务函数直接调用 `sendAll()`。

广播时先在 `clients_mutex` 保护下复制客户端智能指针，再释放列表锁并逐个发送，防止慢客户端长时间阻塞其他线程对在线列表的操作。

### 5. 统一客户端连接关闭流程

引入并整理：

- `stopping`：表示连接已经进入停止状态。
- `requestStop()`：允许其他线程请求停止某个连接。
- `finishClient()`：移除在线客户端并最终关闭 socket。
- `shouldclose`：控制当前 `handleclient()` 线程退出消息处理循环。

理解了 `shutdown()` 与 `close()` 的区别。

确定连接管理规则：发送与关闭由同一把 `send_mutex` 协调，最终的 `close()` 由所属的 `handleclient()` 线程统一完成。

修复了认证失败或昵称重复时直接 `return`，导致无法执行统一清理逻辑的问题。

### 6. 修复广播与私聊的代码问题

主要修复：

- 私聊函数参数类型与传递顺序错误。
- `struct_client` 包含 `mutex` 后无法按值复制的问题。
- 重复获取 `clients_mutex` 引起的死锁。
- 客户端重复添加至 `clients` 的问题。
- 广播时遗漏消息末尾 `\n` 的问题。
- 广播函数声明、定义和调用不一致的问题。

广播时改用 `shared_ptr` 比较客户端对象身份，不再使用可能被其他线程修改或重用的 socket 编号判断发送者。

### 7. 增加异常输入与网络阻塞保护

设置：

```cpp
const int MAX_MESSAGE_SIZE = 4096;
```

在 `handleclient()` 中同时检查：

- 已经接收到的完整消息是否超出长度限制。
- 尚未收到换行符的 `cache` 是否持续增长。

避免异常客户端长期发送不完整消息，导致服务器缓存无限增长。

增加 `isstopping()`，在处理缓存中的下一条消息前检查连接状态。

另外，通过 `setsockopt()` 配置 `SO_SNDTIMEO`，将阻塞式 socket 的发送等待超时设置为 5 秒，降低慢客户端长期占用发送线程和锁的风险。

## 三、今天掌握的核心知识

1. **TCP 字节流特性**：`send()` 和 `recv()` 不存在与应用层消息一一对应的关系，需要自行处理部分发送、粘包和拆包。
2. **应用层协议设计**：通信协议定义消息格式，协议解析与业务处理应分离。
3. **多线程数据竞争**：多个线程同时读写共享变量时，需要统一同步机制。
4. **互斥锁的作用域**：锁保护的是共享资源及需要保持一致性的一段操作，而不只是某一条语句。
5. **智能指针与生命周期**：`shared_ptr` 保证对象存活，但不会自动保证对象内部成员线程安全。
6. **系统资源管理**：C++ 对象销毁与 Linux 文件描述符关闭是不同的资源管理问题。
7. **服务器并发模型**：一个客户端对应一个接收线程，但其他服务端线程仍然可能向这个客户端发送数据。

## 六、今日总结

今天主要完成了 Mytalk 从简单的多人 TCP 聊天程序向具有基本并发管理能力的服务端程序的改造。

相比最初只使用 `socket`、`send`、`recv` 和多个线程实现聊天，现在逐步明确了通信协议、业务处理、线程同步、连接生命周期之间的职责。

最大的收获不是增加了多少代码，而是开始理解**多线程网络程序为什么不能只考虑正常收发消息，还必须考虑部分发送、异常断线、资源释放、数据竞争与对象生命周期**。

本次工作以提高原有功能的正确性、可维护性与稳定性为主，为后续增加数据库、用户系统、离线消息和加密通信打下基础。
